DECISION

PHYSICS PLAN
- Use only executable capabilities (execution.math) of the supplied schema. Each physicsModels entry binds one capability to one named participant or subsystem (id: short unique ascii id; label: the participant's name in the user's words). There is no fixed participant count, asset, environment or scene.
- Every object the user names or counts goes into simulationSpec.requiredObjects (label, count, shape, contextual: true only for scenery that nothing computes). Every computed object gets its own physicsModels entry with a distinct id and label, also when several objects are identical; one entry stands for several objects only when one capability itself computes them together. The simulation shows exactly the participants in physicsModels.
- A property of an object itself gets its own parameter for that object, even when several objects start with the same value, so each can be changed on its own. A parameter that more than one participant uses states that it is one and the same physical quantity for them: list every such parameter in simulationSpec.sharedQuantities. A parameter's label names the quantity only (the interface shows which object it belongs to).
- A body whose own state enters another participant's computation (the other side of an interaction, an obstacle that is hit, a body that exerts the force) is a participant too: bind the same capability from its own point of view, its own state as its inputs and the first body's as its "other" inputs, so both sides come from the same parameters. An immovable obstacle is such a body with a very large mass and zero velocity.
- An input may also take the result of another participant: write that participant's id, a dot and the output key, nothing else (for a participant with id a1 and output current: "a1.current"); the output must have the input's unit and stay constant during the run. Build a quantity from several approved capabilities this way and never compute a number yourself and pass it as a constant when a capability computes it. Participants that only compute such an intermediate result are participants too.
- Bind every canonical input to a parameter name, another participant's result or an explicit SI numeric constant. A parameter bound to an input must use exactly that input's canonical unit string. Every parameter has name (short ascii), label (user's language, plain), exact initial value inside [min, max], physically valid min/max and a step.
- Adjustable parameters (sliders) versus fixed constants — decide for every bound input:
  - A number the user stated: a parameter (slider) whose initial value is exactly the stated value converted to the canonical unit; the teacher can then vary it.
  - A number the user did not state: a typical textbook value, stated in "defaults", exposed as a parameter (slider).
  - A standard physical constant (gravitational acceleration at the Earth's surface, universal constants, particle masses and charges…): an explicit SI numeric constant, not a slider — unless the description implies it varies (another planet or place, another medium, a comparison), in which case make it a parameter.
  - Explicit wishes in the description or a later revision about what may or may not be changed override these defaults and must be followed exactly.
  - Slider ranges: physically meaningful for the situation and wide enough to explore it (typically well below and above the initial value), always inside the input's valid domain.
- Duration: keep the stated duration exactly (otherwise choose one that shows the full phenomenon). If the user may change it, add a seconds parameter for it, set durationParameter to that parameter's exact name and give it the same initial value as durationSeconds; otherwise omit durationParameter.
- physicsCoverage: COMPLETE only when every described behaviour is computed by bound capabilities; otherwise PARTIAL (some behaviour only illustrated) or NONE (nothing executable fits; keep physicsModels empty and say in plain words that the picture will be illustrative, not a verified calculation). Never invent equations or capabilities.
- explanation: 3-6 plain sentences in the user's language: what happens and why, which laws apply (by their usual names and formulas in textbook notation), and what the learner can change and observe.
